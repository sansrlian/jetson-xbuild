# Findings and pitfalls (JetPack 7.2.1 cross builds)

Things learned while making cross builds work, with what jxb does about each. Dated entries; newest last.

## 2026-11-02

| # | Finding | Consequence / what jxb does |
|---|---|---|
| F1 | JetPack 7.2.1 = L4T 39.2.1, Ubuntu 24.04, CUDA 13.2.2 (cudart 13.2.86), cuDNN 9.20.0.46, TensorRT 10.16.2.10, VPI 4.1.4, OpenCV 4.8.0 (NVIDIA build). Board apt: `repo.download.nvidia.com/jetson/{common,som,ffmpeg} r39.2` + pin 600 for `*.nvidia.com` (from `nvidia-l4t-apt-source`). | The sysroot uses exactly these repos and the pin, so NVIDIA's OpenCV 4.8 wins over Ubuntu's 4.6 just like on the board. |
| F2 | **CUDA 13.2 on Orin uses the unified Arm layout `targets/sbsa-linux`** (not `aarch64-linux` as in JetPack 6). The old Renesas-based setup linked against `sbsa-linux`, which is correct. | Toolchain uses `--target-directory sbsa-linux`; sysroot adds an `aarch64-linux -> sbsa-linux` alias for CMake < 4. |
| F3 | x86_64 `cuda-nvcc-13-2=13.2.86-1` exists in NVIDIA's ubuntu2404 repo, the same build as the board's. There is no separate `cuda-cross-*` package needed. | Image installs that nvcc; the board's target tree is bind-mounted into `/usr/local/cuda-13.2/targets/`. |
| F4 | nvcc with `--target-directory` needs target headers that ship in `cuda-nvcc-13-2` (e.g. `fatbinary_section.h`), not in `cudart-dev`. | arm64 `cuda-nvcc-13-2` is in the sysroot set. |
| F5 | CMake's `FindCUDAToolkit` probes `nvcc -v` without flags, so it picked up the **x86_64** CUDA include dir for C++-only targets. | Image prepends `_TARGET_DIR_ = targets/sbsa-linux` to `nvcc.profile` and sets `NVCC_CCBIN=aarch64-linux-gnu-g++`: the toolkit in the image only targets the board; even a plain `nvcc x.cu` yields aarch64. |
| F6 | CMake passes no `--sysroot` when the host compiler links pure CUDA targets. | Toolchain puts `--sysroot` into the linker flags too, and `-Xcompiler=--sysroot=…` into CUDA flags. |
| F7 | Ubuntu's cross GCC always searches its tooldir (`/usr/aarch64-linux-gnu/include`, libstdc++ headers) before the sysroot. libstdc++ is identical (14.2.0-4ubuntu2~24.04.1); glibc differs only in Ubuntu patch level (2.39-0ubuntu8 vs 8.9). | Accepted; `jxb-elfcheck` verifies linkage. TODO: also check GLIBC_/GLIBCXX_ symbol versions. |
| F8 | **The official ONNX Runtime CUDA EP plugin v0.3.0 for linux-aarch64 has SASS only for sm_89/90a/120a/121a and no PTX** — it cannot run on Orin (sm_87). | GPU inference with ORT on Orin needs an sm_87 build of ORT (CUDA/TensorRT EP). Next step in PLAN.md. |
| F9 | The ORT 1.31.0 release tarball's `onnxruntimeConfig.cmake` points to `lib64/` and `include/onnxruntime/`, which the tarball doesn't have. | Sysroot builder adds `lib64 -> lib` and an `include/onnxruntime/` link dir. |
| F10 | SAM's `object_detection_package` hard-codes `/opt/onnxruntime` (board path). | Profile `[container] board_paths`: the dev container maps such paths to the sysroot copy (read-only). |
| F11 | **ROS 2 bug:** `rosidl_adapt_interfaces.cmake` reads its tuple file with `file(STRINGS)` without `ENCODING UTF-8`, which splits lines at non-ASCII bytes. Any interface package under a path like `…/HochschuleMünchen/…` fails with `list index: 1 out of range`. | `sysroot/fixups.toml` patches the sysroot copy. Only hits host builds (board paths are ASCII). Worth reporting upstream. |
| F12 | Jazzy's rosidl names Python extension modules without SOABI suffix (`*_s__rosidl_typesupport_c.so`), which imports fine on the board. | Toolchain still sets `Python3_SOABI=cpython-312-aarch64-linux-gnu` for packages that use it; test checks no x86_64-tagged module is produced. |
| F13 | CV-CUDA 0.16.0 and VPI 4.1 debs create their CMake config links and `ld.so.conf.d` entries in `postinst` with `ln -s` (and shell variables), not `update-alternatives`. | Builder replays `update-alternatives --install` and literal `ln -s` (with simple variable expansion) from postinst scripts. |
| F14 | Rebuilding the sysroot swaps its directory; a running container keeps the old (deleted) bind mount. | `jxb sysroot build` recreates the dev container with the same workspaces. |
| F15 | The SAM stack uses ROS 2 **Kilted** APIs (`message_filters::Subscriber::subscribe(node, topic, int)`, DepthAI v3). Jazzy's apt has depthai 2.31. With `jp721-jazzy`, 22/24 SAM packages cross-build; `image_processing_package` and `oak_camera_package` don't. | Profile `jp721-kilted` (Kilted is Tier-1 on Ubuntu 24.04, so it runs natively on stock JetPack 7.2.1). |
| F16 | `ros.key` from rosdistro is a binary keyring; apt's `signed-by` treats `.asc` as ASCII-armored. | Builder names downloaded keys by content (`.asc`/`.gpg`). |
| F17 | ROS `cv_bridge` (packages.ros.org) links Ubuntu's OpenCV 4.6; NVIDIA's pinned OpenCV 4.8 (JetPack 7.2.1, **no CUDA modules**) made every cv_bridge node load both versions (`libopencv_core.so.406 … may conflict with libopencv_core.so.408`). The same happens when building natively on a board with `nvidia-opencv-dev`. | Profiles pin Ubuntu's `libopencv-dev` (priority 700 over NVIDIA's 600): one OpenCV per process. |
| F18 | SAM's `image_processing_package` sets `CMAKE_CUDA_ARCHITECTURES "75;80;86;89"` unconditionally, so no sm_87 code is built. sm_86 SASS runs on sm_87 (same major, lower minor), so it works, just not tuned for Orin and with 4× the CUDA compile work. | Suggestion for the SAM repo: `if(NOT DEFINED CMAKE_CUDA_ARCHITECTURES)` around it and include 87; jxb then builds exactly sm_87. |
| F19 | Result 2026-11-02: the full SAM workspace (24 packages, all except `pylon_camera_package` (Basler SDK) and the acados packages) cross-builds with `jp721-kilted` in 2:18 min cold / 1:14 min with ccache, 0 linkage problems. With `jp721-jazzy` 22/24 build (F15). | Remaining: acados cross build (trajectory planner), Pylon SDK as extra, on-board runtime tests. |
| F20 | acados: `acados_model_package` renders and compiles its solver at build time with acados_template (Python + casadi + `t_renderer`) and a generated Makefile that uses `$(CC)`; then `AcadosOcpSolver()` dlopens the result. | acados 0.5.2 is cross-built (`extras/acados/build.sh`, BLASFEO `ARMV8A_ARM_CORTEX_A76`) into `/opt/acados` (sysroot extra, container board path). The image provides `/opt/acados-host` (x86 `t_renderer`, links to the board's headers/libs) and the generator Python packages in `/opt/codegen-python`. `cross-colcon-build` sets `CC`/`CXX` to the board compiler and `JXB_CROSS_BUILD=1`; a fixup makes acados_template skip the dlopen in that case. |
| F21 | casadi 3.8 warns "not tested with acados" (acados 0.5.2 tests 3.7). pip `--target` pulled numpy 2.x, which breaks Debian's scipy. | Image pins `casadi==3.7.2` and `numpy<2` (also what SAM's model package requires). |
| F22 | **CUDA 13.2 bug** [NVIDIA/cccl#8833](https://github.com/NVIDIA/cccl/issues/8833): `cub/device/device_transform.cuh` and `cub/device/dispatch/tuning/tuning_transform.cuh` specialize `cuda::proclaims_copyable_arguments` outside its namespace. For .cu files nvcc's front end (EDG) re-emits that as `struct ::cuda::__4::proclaims_copyable_arguments<...>`, which GCC 13/14 reject ("global qualification of class name is invalid"), so dropping the `::` in the source (the fix suggested in the issue) is not enough. Breaks ONNX Runtime's CUDA EP, also natively on the board. | Sysroot fixups declare both specializations inside `namespace cuda { inline namespace _LIBCUDACXX_ABI_NAMESPACE {...} }`. |
| F23 | Feasibility of Lyrical on the 24.04 board (container mode, D2a): ROS Lyrical arm64 exists for Ubuntu 26.04 (`repo.ros2.org … resolute`, depthai 3.10, cv_bridge 4.1). NVIDIA's CUDA repo for ubuntu2604/sbsa has only CUDA **13.3** (board: 13.2) and **no TensorRT**. | Design for D2a: Ubuntu 26.04 container userspace with ROS Lyrical; CUDA/cuDNN/TensorRT from the board via nvidia-container-toolkit (24.04-built libs run on 26.04's newer glibc). Cross-build sysroot = Ubuntu 26.04 arm64 + Lyrical + the r39.2 CUDA/TRT dev debs (extract-only, so no Ubuntu-codename conflict). Needs a check on the Nano that the JP 7.2.1 container runtime mounts these libs. |
| F24 | ONNX Runtime 1.31's CUDA EP has ~680 `.cu` files, 607 of them contrib ops; a full sm_87 build would take ~7 h on the 20-core / 15 GB workstation. `--disable_contrib_ops` is not an option with the TensorRT EP (it needs the contrib `EPContext` node). | `extras/onnxruntime/build.sh` defaults to `FLAVOR=lean`: contrib ops on, but the optional LLM kernel families off (TensorRT fused attention cubins, FP4 MoE, fpA×intB GEMM, INT4/FP8 KV cache, flash/memory-efficient attention). `FLAVOR=full` stays available. |
| F25 | With Ubuntu 26.04's QEMU 10.2, the **default** aarch64 CPU model raises SIGILL when Python imports extension modules built by GCC 15 for `-mcpu=cortex-a78ae`; `-cpu max`, `neoverse-n1` and `cortex-a76` run them (no `udf`/`brk` in the code). Ubuntu 24.04's QEMU 8.2 default was fine. | Profiles set `[board] qemu_cpu = "cortex-a76"` (closest QEMU model to Orin's Cortex-A78AE: ARMv8.2-A, no SVE); the test suite always passes `-cpu`. |
| F26 | JetPack 7.2 installs the CUDA driver per GPU variant under `/opt/nvidia/l4t-gpu-libs/{nvgpu,openrm}`; the board's boot service `nv-load-gpu-libs.sh` (nvidia-l4t-init) publishes the active one via `/etc/ld.so.conf.d/000-nvidia-gpu-libs.conf` and `libcuda.so{,.1}` links in `/usr/lib/aarch64-linux-gnu`, and writes the container CSV (`host-files-for-container.d/l4t.csv`) used by nvidia-container on Jetson. Without that, `libcuda.so.1` (needed by ORT's CUDA EP) does not resolve. | Builder replays the boot step for the profile's `[board] gpu_variant` (Orin: `nvgpu`). The CSV mechanism confirms the Lyrical container plan (F23). |
| F27 | Result: ONNX Runtime 1.31.0 GPU build (`FLAVOR=lean`, CUDA + TensorRT EP, 269 sm_87 kernels, 33 MB tarball) replaces the CPU release in all three sysroots; under QEMU it lists `TensorrtExecutionProvider CUDAExecutionProvider CPUExecutionProvider`. | Board run of `ort_smoke --ep cuda/tensorrt` pending (SSH key). |
| F28 | `jp721-lyrical` (Ubuntu 26.04, GCC 15, CMake 4.2, Python 3.14, numpy 2.3): test suite 12/12; SAM 25 packages build, 0 linkage problems. `localization_package` fails on Lyrical natively too (SAM image): Lyrical's tf2 0.45 removed `tf2/LinearMath/Quaternion.h` (only `.hpp`). `jxb-rosdeps` had `noble` hard-coded, so Lyrical keys silently didn't resolve. | SAM fix: include `Quaternion.hpp`. `jxb-rosdeps` uses the profile's `[sysroot] codename` and fails on unresolved keys. |
| F29 | Isaac ROS `release-4` apt repo (noble): 156 `ros-jazzy-isaac-ros-*` packages for **amd64**, but for **arm64 only 55 packages (CLI, Python shims), no Isaac ROS binaries**. On Jetson, Isaac ROS 4.x/5.0 comes from source (NVIDIA-ISAAC-ROS repos, branches up to `release-5.0`) or NVIDIA's containers; prebuilt GXF/vendor binaries are in Git LFS. | Next work item: cross-build Isaac ROS from source (needs `git-lfs` in the image, a Jazzy-only profile, GXF aarch64 prebuilts). |
| F30 | **Isaac ROS 5.0 (2026-09-21) moved to ROS 2 Lyrical** and NVIDIA publishes Lyrical for Ubuntu 24.04 on its Isaac ROS Buildfarm (`https://isaac.download.nvidia.com/isaac-ros/ubuntu/main noble main`, 2673 arm64 / 2700 amd64 `ros-lyrical-*` packages; signed with `isaac-ros/repos.key`). Isaac ROS itself for JetPack 7.2: `isaac-ros/release-5.0 noble-jetpack` (148 Isaac packages, arm64). NITROS was replaced by Lyrical's `rosidl::Buffer` with a CUDA backend (`cuda_buffer`). Isaac ROS 4.6 (2026-08) was the first with Orin + JetPack 7.2 support (Jazzy). Of SAM's dependencies only `depthai` is missing on the Buildfarm. | Profile `jp721-lyrical-isaac`: Lyrical native on stock JetPack 7.2.1 (= D2b, no own ROS build) + Isaac ROS 5. Image adds the Buildfarm (distro packages, NVIDIA key) and packages.ros.org (tools). Test package `tests/isaac_ws` exercises the CUDA buffer backend. Isaac's CV-CUDA is 0.14 (SAM image: 0.16). |
| F31 | Legacy `FindCUDA` (used by `isaac_ros_common`) takes the cross-compile target dir only from the **environment variable** `CUDA_TOOLKIT_ROOT`; without it, `find_package(CUDA)` fails with "missing CUDA_INCLUDE_DIRS CUDA_CUDART_LIBRARY" although it found nvcc 13.2. The Buildfarm's Lyrical packages also need `python3-catkin-pkg-modules`/`python3-rosdistro-modules` from packages.ros.org (noble). | Toolchain sets `ENV{CUDA_TOOLKIT_ROOT}`. `jp721-lyrical-isaac` sources include packages.ros.org noble. `jxb-rosdeps` resolves ROS keys via `rosdep_fallback_codename` (resolute) when the distro isn't released for the board's Ubuntu; the sysroot builder drops workspace-set packages no repo has (depthai) with a warning. |
| F32 | Result `jp721-lyrical-isaac`: test suite 13/13 incl. Isaac ROS 5 (TensorRT node lib + `rosidl::Buffer` CUDA backend); SAM 24 packages, 0 linkage problems; not building: `oak_camera_package` (no depthai for Lyrical/noble), `localization_package` (Lyrical tf2 `.hpp`). | depthai for this profile: cross-build depthai-core/depthai-ros as an extra, or keep the OAK node on Kilted. |
| F33 | **Bug in the jxb toolchain (fixed):** it `set()` `CMAKE_FIND_ROOT_PATH`. Toolchain files are read several times per configure, and vcpkg.cmake re-includes the chainloaded toolchain on every read but adds its own roots only on the first, so vcpkg's installed dir vanished from the roots and `find_package` re-rooted it into the sysroot (depthai's port `basalt-headers` could not find the just-built Sophus; Eigen3 silently came from the sysroot). | The toolchain appends its roots and de-duplicates. |
| F34 | depthai-core 3.10 (ROS release source `luxonis/depthai-core-release`, tag `release/<distro>/depthai/<version>`) bootstraps vcpkg at configure time and builds ~87 bundled ports. Cross-building works with an overlay triplet `arm64-linux-jxb` that chainloads the jxb toolchain (`VCPKG_CHAINLOAD_TOOLCHAIN_FILE`) and passes the jxb variables through (`VCPKG_ENV_PASSTHROUGH`); host tools stay `x64-linux`. vcpkg needs `zip` (added to the image). | `extras/depthai/build.sh` builds it into `/opt/ros/<distro>` (like the apt package); `jp721-lyrical-isaac` picks it up as an optional extra. |

| F35 | Board `nano-001` (Orin Nano, JetPack 7.2.1, L4T R39.2.1, 25 W mode, 7.3 GB RAM, NVMe): CUDA 13.2.86, TensorRT 10.16.2.10, VPI 4.1.4 match the sysroot; **cuDNN 9.25.1** (JetPack: 9.20) and Jazzy from the 2026-06 sync (rclcpp 28.1.21 vs 28.1.22 in the sysroot) differ (ABI-compatible patch levels). NVIDIA OpenCV 4.8 and the board's own `/opt/onnxruntime` 1.31.0 (CPU build: no CUDA provider registered) and `/opt/acados` are installed; Docker + `nvidia-ctk` are present. **The board clock is at 1970** (no NTP sync). | `jxb board check` shows the diffs. Pinning the sysroot to the board's package versions (or upgrading the board) is a follow-up. |
| F36 | **Cross-built tests on the Nano: 8/8** — CUDA (RDC, cuBLAS), TensorRT engine build + inference, ONNX Runtime CPU/**CUDA**/**TensorRT** EP (jxb's build), ONNX library, ROS 2 node with CUDA + TensorRT + cv_bridge + custom interface, Python import of the cross-built messages. | `jxb test --board <name>` (writes only to `~/jxb/<profile>`). |
| F37 | colcon's `setup.*` and ament's `parent_prefix_path` index recorded the sysroot's `/opt/ros/<distro>` as underlay (host path on the board). The board runner failed under `set -u` when sourcing ROS setup scripts. | `cross-colcon-build` rewrites the sysroot prefix to the board path after each build; the runner sources ROS setup without nounset. |
| F38 | **SAM `object_detection_package`, cross-built (Jazzy), runs on the Nano with "Inference device: GPU"** on jxb's ONNX Runtime CUDA build (the board's `/opt/onnxruntime` only gives CPU). The board's `~/ros2_ws/assets/models/model.onnx` has two outputs and does not fit the current SAM code (one output, `[1,300,6]`); tested with the training repo's S0 model. | `jxb deploy` ships the profile's `[deploy] runtime` dirs (jxb's ORT, acados) to `~/jxb/<profile>/runtime/` and `jxb run` puts them first on `LD_LIBRARY_PATH`; the board's `/opt` stays untouched. |
